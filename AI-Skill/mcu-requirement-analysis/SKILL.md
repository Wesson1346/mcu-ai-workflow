# 单片机系统需求分析（生成功能清单）

## Overview

将用户的模糊想法（"我想做一个XX系统"）逐步转化为一份清晰的**系统需求功能清单**。该清单是后续硬件选型、功能拆解、电路搭建、模块编程的输入文档，保证后续所有开发步骤不跑偏。

## 核心原则

- 需求分析不是写代码，是想清楚要做什么
- 先自己思考，再用 AI 辅助
- 做出来一个能跑的完整系统，比做半个好

## 工作流程：需求分析三步法

严格按照以下三步执行。每完成一步，将结果告知用户，征求确认后再进入下一步。

### 第一步：一段话描述

把用户的模糊想法整理成一段话描述，使用以下模板：

```
==设计一个基于STM32的[系统名称]，实现[核心功能]。==
```

**要求**：这段描述必须具体，包含以下要素：
- 系统名称
- 监测/采集什么数据（传感器）
- 自动控制逻辑（根据什么条件，做什么动作）
- 本地交互方式（按键、OLED显示等）
- 远程交互方式（App、蓝牙、云平台等，如果有）

**示例对照**：
- ❌ "我想做一个基于STM32智能温控风扇系统"（太模糊）
- ✅ "设计并实现一个基于STM32智能温控风扇系统。系统能够实时监测环境温度，并根据设定的温度阈值或控制算法，自动调节风扇转速，实现节能和智能化控制。同时，通过本地按键提供人机交互界面用于参数设置和状态显示，能够通过手机端实时显示采集到的温度等数据，并且能够对系统进行风扇模式切换等远程控制。"

**引导提问**：如果用户信息不足，依次询问以下问题（不要一次全问，先问最关键的）：
1. 系统主要实现什么功能？
2. 用什么传感器采集数据？
3. 需要控制什么执行器（电机/继电器/舵机等）？
4. 需要本地显示（OLED等）和按键操作吗？
5. 需要远程通信（蓝牙/WiFi/App/云平台）吗？

### 第二步：功能清单（自己先想 + AI生成）

本步骤分两个子步骤：

**① 引导用户先自己想**：让用户先独立列出系统功能清单，哪怕只想到 3 个功能也行。这一步让用户知道自己与 AI 的差距，以及 AI 的价值。

**② 生成 AI 功能清单**：将第一步的一段话描述发给 AI 模型，使用 `references/prompt-templates.md` 中的「功能清单生成模板」，生成结构化功能清单。生成的清单必须：
- 按**核心功能**和**加分功能**分类
- 每个功能包含具体细节（数据来源、控制逻辑、交互方式、参数等）
- 覆盖：数据采集、显示、控制逻辑、本地交互、通信、报警、附加功能

**③ 合并调整**：将用户自己想的清单与 AI 生成的清单合并，删掉重复项，补充遗漏项，形成完整的候选功能清单。

### 第三步：功能取舍

AI 生成的功能清单比较全面，但不需要全部实现。引导用户使用**功能取舍四问法**对每个加分功能进行评估：

```
① 这个功能是"核心"还是"加分"？
② 我的时间够不够做？
③ 我的技术能不能做？
④ 去掉这个功能，系统还能不能用？

核心功能全保留，加分功能按②③④判断。
```

**输出**：最终确认保留的功能清单，标记出核心功能与加分功能，以及被舍去的功能及理由。

## 产出物：直接输出 md 文档

最终必须将功能清单**保存为一份 md 文档**（不要只停留在对话输出）。步骤如下：

1. 三步法全部完成后，基于 `assets/feature-list-template.md` 模板，填充本次系统的实际内容，生成完整的功能清单文档
2. 使用 Write 工具，将文档保存到**当前工作目录**（用户项目的根目录）
3. 文件命名规则：`[系统名称]需求功能清单.md`（例如：`智能台灯系统需求功能清单.md`）
4. 保存后告知用户文件路径，并简要总结清单要点

文档内容应包含：
- 系统名称与一段话描述
- 核心功能列表（每个功能含具体实现细节）
- 加分功能列表
- 被舍去的功能及取舍理由
- **文档末尾必须附加提示**：说明功能清单由 AI 辅助生成、仅供参考，具体功能的取舍与调整需用户自行决策

## 注意事项

- 功能清单必须按"核心/加分"分类，这是后续功能取舍的基础
- 不要替用户做取舍决定，只提供评估框架，由用户根据时间、技术、需求决定
- 生成的功能清单要具体到"做了什么、用什么实现"，不要只有功能名字
- **文档输出是必须的**：每次执行完三步法，一定要用 Write 把功能清单保存为 md 文档，不能只在对话里输出
- 若当前工作目录存在同名文件，先询问用户是否覆盖，或生成带日期后缀的文件名
