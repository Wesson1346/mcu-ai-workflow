# 单片机系统功能拆解（生成模块拆解文档）

## Overview

将一份**需求功能清单**（来自 mcu-requirement-analysis）和一份**硬件选型清单**（来自 mcu-hardware-selection）作为输入，把一个大系统拆解成一个个**可独立开发、独立测试的硬件模块**，每个模块写一张"模块卡片"，最后补一张"模块关系图"说明模块间如何协作。产出物是《系统名称功能拆解文档.md》，作为后续电路搭建、模块编程、功能联调的输入。

## 核心原则

- **拆解不是写代码**，是把大功能变成小模块，每个模块可独立开发、独立测试
- **一个硬件外设 = 一个独立模块**：数一下用到了几个硬件，就有几个模块
- **先看整体再拆**：先弄清系统由"传感器/执行器/显示/交互/通信/报警"哪几类组成，再逐项拆
- **模块编号 = 单模块编程递加顺序**：模块卡片按"后续编程由易到难、层层递加"的顺序编号，让每实现一个模块，系统就多一项可独立演示的功能；不照搬需求功能编号，与需求编号的对应关系用映射表说清（见"第一步"）
- **拆完要能拼**：用一张模块关系图说清数据流，回答"拆完怎么拼回去"
- **只做拆解，不做实现**：不分配引脚、不写驱动代码、不写主控 while(1) 逻辑，那些属于电路搭建和模块编程阶段
- **纯软件功能不单独成模块**：App 远程控制、阈值设置等复用已有硬件或纯逻辑的功能，不新增硬件模块，标注即可

## 需求功能清单 vs 功能拆解文档（两份文档的区别）

很多同学容易把这两份文档搞混，执行本 skill 前先认清定位：

| | 需求功能清单 | 功能拆解文档 |
| --- | --- | --- |
| 回答的问题 | "系统要做什么" | "系统由哪些模块组成、怎么配合" |
| 视角 | 用户/需求视角（软件视角） | 开发者视角（硬件视角） |
| 内容 | 用大白话描述功能行为：1秒采集一次、转速0~100%、超温报警 | 把功能落到具体硬件型号上，每个硬件一张模块卡片 |
| 一条功能对应 | 一个功能可能对应多个硬件 | 一个硬件外设 = 一个模块 |
| 纯软件功能 | 正常列为一条功能（如③自动控温、⑧App控制） | 标注"纯软件，无新硬件"，不单独成模块 |

**典型例子**："手动调速"在需求功能清单里只是风扇调速下面的一个子功能描述；但在拆解文档里，它对应独立硬件电位器，单独成为一个模块。

**开发流程中的位置**：需求功能清单 → 硬件选型清单 → 功能拆解文档 → 电路搭建 → 模块编程。简单说：**需求功能清单是"做什么"的目标清单，功能拆解文档是"怎么拆成零件来做"的施工图**。

**输出要求**：生成的功能拆解文档应在"一、拆解依据"后附带上述对比说明（内容见 `assets/decomposition-template.md` 模板），帮助读者区分两份文档。

## 工作流程：功能拆解二步法

严格按照以下步骤执行。每完成一步，将结果告知用户，征求确认后再进入下一步。

### 第一步：提取硬件模块

**输入方式（两种都支持）**：
- 方式 A：用户提供需求功能清单 + 硬件选型清单 md 文档路径，用 Read 读取
- 方式 B：用户直接在对话中粘贴两份清单文本

**操作**：
1. 读取需求功能清单，列出**每一项核心功能/加分功能**
2. 读取硬件选型清单，把每项功能对应到具体硬件
3. 建立"需求功能 → 硬件 → 模块编号"的映射表。**模块编号不照搬需求功能编号**，按下方"模块编号编排规则"重新编排为 模块1、模块2…，映射表同时保留需求功能编号，保证两套编号一一对应、无遗漏

**模块编号编排规则（模块编号 = 单模块编程递加顺序）**：

模块编号服务于后续"模块编程"的递加实施——**每实现一个模块，系统就多一项可独立演示、可独立验证的功能**。通用编排顺序参考：

| 实施阶段 | 模块类型 | 典型示例 | 理由 |
| --- | --- | --- | --- |
| 先做 | 数据源/传感器 | DHT11 温度采集 | 先有可靠数据 |
| 先做 | 显示模块 | 0.96寸 OLED | 把数据显示出来，兼作后续所有模块的调试窗口（可显示中间量/阈值/状态） |
| 再做 | 执行器 | 风扇（PWM）、LED | 手动给占空比即可独立验证输出 |
| 再做 | 交互输入 | 按键、编码器 | 界面/模式/参数调节 |
| 再做 | 报警/提示 | 有源蜂鸣器 | 简单 GPIO 输出 |
| 再做 | 手动模拟量输入 | 电位器（ADC） | 第二路输入源 |
| 最后 | 通信模块 | ESP8266/WiFi | 需汇总前面所有数据与状态，放最后上云联调 |

要点：
- 模块编号 = 文档卡片编号 = 关系图编号 = 后续编程实施顺序，先实现的编号小
- 编号不必与需求功能编号数字一致（如需求①温度采集虽列在第一项，但显示模块对调试帮助更大时可排在模块2，示例见 `references/case-study-fan.md`），靠映射表对应；但"一个硬件 = 一个模块"的总数不能少
- 顺序是参考不是死板模板，以"递加每一步都能演示一项功能"为原则做合理调整

**关键判断规则**：
- **纯软件功能**（如 App 远程控制、阈值设置）：复用已有硬件或纯逻辑，**不单独成模块**，在映射表里标注"（纯软件，无新硬件）"
- **一个硬件可能服务多个功能**：如 OLED 同时显示温度、转速、模式，只算一个模块
- **不要遗漏**：对照硬件清单逐项打勾，确保每个硬件都有对应模块

**输出**：一张"需求功能（保留原始编号）→ 硬件 → 模块编号（=编程顺序）"映射表 + 一份按编程递加顺序排列的"硬件模块清单"（列出所有模块，可标注递加理由），告知用户。

### 第二步：写模块卡片

模块卡片按模块编号（=编程递加顺序）从模块1开始逐张书写，编号越小越先被独立开发与验证。每个硬件写一张"模块卡片"。**固定 4 个字段**，保持信息密度均衡：

```
模块名称：[硬件的名字]
├─ 硬件型号：[具体型号]（[接口]）
├─ 功能描述：[做什么，含输入→输出、触发条件、数据给谁用]
└─ 验证方法：[怎么确认这个模块是好的]
```

**功能描述要"详细但不冗长"**，尽量包含：
- 采集/控制细节（如"每隔1秒读取""PWM占空比0~100%"）
- 输入→输出关系（接收什么、输出什么）
- 触发条件（自动模式由谁触发、手动模式由谁给定）
- 数据给谁用（供 OLED 显示 / 主控逻辑判断 / 云平台上传）

**验证方法要"可观察"**：描述能直接看到/测到的现象（如"手捏传感器数值变化""遮挡光敏数值变小""GPIO拉高蜂鸣器响"）。

### 第三步：画模块关系图（说明模块怎么协作）

拆解不只是列清单，还要让学习者知道模块之间怎么配合。画一张 ASCII 模块关系图，并附一句"数据流总结"：

```
                     ┌──────────────┐
   模块1 DHT11 ──────▶│              │──▶ 模块2 OLED（显示）
   模块4 按键  ──────▶│   主控逻辑     │
   模块6 电位器 ─────▶│  (联调阶段实现) │──▶ 模块3 风扇（PWM）
   模块7 ESP8266 ◀───▶│              │──▶ 模块5 蜂鸣器（报警）
  （App指令/上传数据） │              │
                     └──────────────┘
```

**要点**：
- 用箭头标出**数据流向**（谁的数据给谁用、谁的指令控谁）
- 注明"主控逻辑"在联调阶段实现，这里只画关系，不写代码
- 附一句数据流总结，如"传感器提供数据 → 主控判断 → 控制执行器 → 状态显示 → 数据上传云平台 → App 指令再回主控"
- 关系图中的编号与模块卡片编号一致（模块编号 = 编程递加顺序）

### 第四步：自检

用自检清单核对拆解质量：

```
□ ① 模块数量对不对？  数一下用到的硬件，每个硬件一个模块，有无遗漏
□ ② 每个模块能否独立测试？  能单独验证 = 好模块
□ ③ 有没有"纯软件"功能混进来？  App控制/算法逻辑属于主控逻辑，不单独成模块
□ ④ 模块编号是否按"编程递加顺序"编排？  先数据源/显示（调试窗口），后执行器/交互/报警/通信，不照搬需求编号
□ ⑤ 模块顺序是否便于递加编程？  每实现一个模块，系统即可多演示一项功能
□ ⑥ 映射表能否对上需求功能编号？  映射表保留需求功能编号，两套编号一一对应、无遗漏
□ ⑦ 模块关系是否清楚？  能说出每个模块的数据给谁用、接收谁的指令
```

### 第五步：输出 md 文档

基于 `assets/decomposition-template.md` 模板，生成并保存功能拆解文档：

1. 使用 Write 保存到**当前工作目录**（用户项目根目录）
2. 文件命名：`[系统名称]功能拆解文档.md`（例如：`智能温控风扇系统功能拆解文档.md`）
3. 文档结构：拆解依据（含"需求功能清单 vs 功能拆解文档"对比说明）→ 硬件模块清单 → 模块卡片（逐张，按编程递加顺序）→ 模块关系图 → 自检结果
4. 保存后告知用户文件路径，并简要总结拆解要点（几个模块、模块顺序一句话、模块关系一句话）

## 注意事项

- **输入必须是"需求功能清单 + 硬件选型清单"**：如果用户只有模糊想法，先引导用户用 `mcu-requirement-analysis` 生成需求功能清单、用 `mcu-hardware-selection` 生成硬件选型清单，再进入本 skill
- **只做拆解**：本 skill 绝不分配引脚、不画接线图、不写驱动代码、不写主控 while(1) 逻辑，那些属于"系统电路搭建"和"模块编程/联调"阶段
- **模块卡片按编程递加顺序输出**：模块编号 = 单模块编程实施顺序（先数据源/显示调试窗口，再执行器/交互/报警/手动输入，通信类数据依赖最多放最后），不为凑需求编号而打乱实施顺序
- **模块卡片字段固定为 4 个**：模块名称/硬件型号/功能描述/验证方法，避免信息杂乱、密度不均
- **纯软件功能不单独成模块**：App 控制、阈值设置等复用硬件的功能，标注即可，不新增模块
- **风扇等执行器形态以硬件选型清单为准**：硬件清单选的是"裸器件+驱动"还是"模块化直驱"，模块卡片就写什么，不擅自改
- **文档输出是必须的**：每次执行完二步法，一定要用 Write 把拆解文档保存为 md 文档，不能只在对话里输出
- 若当前工作目录存在同名文件，先询问用户是否覆盖，或生成带日期后缀的文件名
