# OneNET 云平台接入要点（ESP8266 + MQTT 属性上报 / 指令下发）

本文档记录 STM32F103 通过 ESP8266 连接 OneNET 云平台、进行**物模型属性上报**与**接收 App 下行指令**时的实测经验与踩坑点。生成云通信相关驱动代码时务必参考。

> **平台控制台怎么配**（注册 → 创建产品 → 物模型 → Token → 用 MQTT.fx 验证）见
> `references/onenet-setup-guide.md`。本文档只讲**代码层**的坑。
> 顺序上建议：先按 setup-guide 把平台配通并用 MQTT.fx 验证，再动单片机代码。

## 零、可复用源码（完整跑通）

生成 OneNET 相关代码时，**不要从零编写**，直接**整份复制** `assets/communication/` 下已实测跑通的源码（详见 SKILL.md 第 4 步"OneNET 通信代码生成约定"）：
- `esp8266.c/h` — AT 指令驱动（USART2）。**接收层已是修复版**：按 `+IPD,<len>:` 长度精确取帧、发送路径只丢 AT 回显、带临界区保护（见第七节，务必读）
- `onenet.c/h` — OneNET 应用层。含设备配置区、物模型主题宏、**属性设置回调接口** `OneNet_RegisterPropertySetCb()` 与指令回执
- `MqttKit.c/h` + `Common.h` — MQTT 协议层
- `cJSON.c/h` — JSON 解析

复制后只需改两个配置区：
- `onenet.h` 顶部的 `ONENET_PROID` / `ONENET_DEVID` / `ONENET_TOKEN`（物模型主题由这三个宏自动拼接）
- `esp8266.c` 顶部的 WiFi 账号密码与 MQTT 服务器地址

## 一、连接框架

- STM32 通过 USART2/3 连接 ESP8266，ESP8266 以 AT 指令建立 TCP/MQTT 连接 OneNET
- 属性上报主题（发布）：`$sys/{product_id}/{device_name}/thing/property/post`
- 设备认证：一型一密（product_id + device_name + device_secret）或三元组（product_id/device_name/device_secret），由 onenet.c / mqttkit 库负责登录
- **⚠️ 属性上报必须用 QoS1**：`MQTT_PacketPublish` 的 qos 传 `MQTT_QOS_LEVEL1`（已实测，QoS0 会被 OneNET 平台直接丢弃）

## 二、⚠️ 核心坑点：属性值必须用 {"value":...} 包装（易踩坑）

OneNET **新版物模型**的**属性上报格式**，属性值必须包裹在 `{"value": ...}` 对象里，否则平台**校验失败并被静默丢弃**（不报错，但数据永远不更新）。

### 正确格式（平台能识别）
```json
{"id":"1","version":"1.0","params":{"temp":{"value":20}}}
```

### 错误格式（平台静默丢弃）
```json
{"id":"1","version":"1.0","params":{"temp":20}}
```

### 判断依据
- 平台侧若收到的是：`{"params":{"temp":{"value":20}}}` → 说明新版物模型格式
- 上报后 `MQTT Publish Send OK`（传输层 ACK 成功）**但**物模型数据不更新 → 几乎可以断定是属性值缺少 `{"value":...}` 包装，被物模型解析校验时丢弃

## 三、⚠️ 核心坑点 2：bool 类型属性必须上报 true/false，写成 1/0 会整包被拒（已实测）

物模型里数据类型为 **bool** 的属性，上报值必须是 **JSON 布尔字面量 `true` / `false`**，
**不能写成数字 `1` / `0`**。

> 建属性时填的"数据定义 `true=1, false=0`"是**平台内部的取值映射**（供 App / 平台侧展示用），
> **不是**让你上报数字 1/0。上报时仍要用 `true` / `false`。

### 正确格式
```json
{"id":"1","version":"1.0","params":{"fan_on":{"value":true},"mode":{"value":false}}}
```

### 错误格式（bool 属性写成数字，整包被拒）
```json
{"id":"1","version":"1.0","params":{"fan_on":{"value":1},"mode":{"value":0}}}
```

### ⚠️ 为什么很难查：params 是"整包校验"

`params` 里**只要有一个属性标识符不存在、或数据类型不符**（如 bool 写成 1/0、数值越界），
**整包**都会被物模型校验拒绝，表现是 **所有属性一个都不更新**——即使其余属性完全正确。

所以遇到"多属性全部不刷新"时，**不要以为每个属性都写错了**，
应按「bool 类型 → 标识符拼写 → 数值范围」的顺序逐个排除最可疑的那一个。

### 实测现象（可作为判断依据）

- 串口正常打印 `Cloud Upload: {...}` 和 `Publish Topic: ...`
- 串口**能**收到 `Tips: MQTT Publish Send OK`（QoS1 的 PUBACK）
- 但平台物模型数据一个都不刷新
- 把 bool 属性的 `1`/`0` 改成 `true`/`false` 后，数据立即开始更新

## 四、正确的属性上报代码模板

```c
static void Cloud_Upload(void)
{
	char msgBuf[64];

	/* OneNET 新版物模型属性上报，属性值必须包裹在 {"value":...} 中 */
	sprintf(msgBuf,
		"{\"id\":\"1\",\"version\":\"1.0\",\"params\":{\"temp\":{\"value\":%d}}}",
		g_Temp);

	UsartPrintf(USART_DEBUG, "Upload: %s\r\n", msgBuf);

	/* 发布到属性上报主题 */
	OneNet_Publish(ONENET_TOPIC_POST, msgBuf);
}
```

要点：
- JSON 中的 identifier（如 `temp`）必须与平台物模型里创建的属性标识**完全一致**（大小写/拼写都对），否则同样不更新
- `msgBuf` 容量要留足（上述 JSON 约 53 字节 + 结束符 = 54 字节，`char msgBuf[64]` 够用；属性多时按需加大）
- 上报主题常量（如 `ONENET_TOPIC_POST`）在 onenet.h 中定义，需与平台 product_id / device_name 匹配

## 五、多属性上报模板（含 bool 混排）

```c
sprintf(msgBuf,
	"{\"id\":\"1\",\"version\":\"1.0\",\"params\":{"
	"\"temp\":{\"value\":%d},"
	"\"fan_duty\":{\"value\":%d},"
	"\"temp_low\":{\"value\":%d},"
	"\"temp_high\":{\"value\":%d},"
	"\"mode\":{\"value\":%s},"
	"\"alarm\":{\"value\":%s},"
	"\"fan_on\":{\"value\":%s}}}",
	g_Temp, g_FanDuty, g_TempLow, g_TempHigh,
	(g_FanMode == FAN_MODE_AUTO) ? "true" : "false",
	(g_AlarmFlag != 0) ? "true" : "false",
	(g_FanOn != 0) ? "true" : "false");
```

要点：
- 每个属性值都要单独 `{"value":...}` 包装，多个属性之间用逗号分隔
- **整型属性用 `%d`，bool 属性用 `%s` 配 `"true"`/`"false"`**，两类不能套用同一种格式化
- 缓冲区按属性个数留足：上面这条实测约 196 字节 + 结束符，`char msgBuf[256]` 起
- 属性顺序建议固定（先只读、后读写），便于与平台物模型表逐行核对

## 六、调试建议

上报后平台数据不更新时，按下面顺序排查（**这些都是"平台静默丢弃"，串口一律不报错**）：

1. **看串口打印的 Upload JSON**，确认每个属性值都包在 `{"value":...}` 里
2. **核对数据类型**：bool 属性有没有误写成 `1`/`0`（见第三节），整型属性有没有越界
3. **核对标识符**：平台物模型属性标识名与代码里 identifier 逐字核对（含大小写、下划线）
4. **确认物模型已"发布"**：OneNET 控制台改完物模型必须点发布，否则平台照样收包、回 ACK，但数据不写入
5. **确认设备在线**：设备显示离线说明 MQTT 连接已断
6. 以上都对仍不更新 → **订阅属性上报回复主题**
   `$sys/{pid}/{dev}/thing/property/post/reply`，平台会把校验结果
   （`{"id":"1","code":200,"msg":"success"}` 或错误码）通过 MQTT 下行发回来，在接收分支打印即可看到具体原因

> **核心结论：传输层成功 ≠ 物模型写入成功。**
> `Tips: MQTT Publish Send OK` 只证明平台 MQTT 服务端收下了这个包；
> 物模型校验失败时平台**不会**通过 PUBACK 告知，必须靠上面 1~6 步定位。

## 七、⚠️ 核心坑点 3：ESP8266 接收缓冲区管理（App 下发指令偶发收不到的根因）

### 现象

App / 控制台点开关，设备**有时**收不到；串口**一个字都不打印**（连 `topic: ...` 那行都没有）。

> **"完全没有打印"就是定位线索**：`topic: ...` 那行在协议解析之前、回调之前打印，
> 只要字节取到了就一定会打。连它都没有 → 问题一定在**"收"这一层**，
> 与解析、执行、回执无关。反过来，如果 `topic:` 打了但业务没生效，才是解析/执行的问题。

### 参考源码里的 5 个丢帧点（`assets/communication/esp8266.c` 新版已全部修复）

| # | 位置 | 问题 | 修法 |
|---|---|---|---|
| 1 | `ESP8266_SendData()` 开头的 `ESP8266_Clear()` | 发送前 memset **整个** 512 字节接收缓冲区，把**正在到达**的下行帧一起清掉 | 改成 `ESP8266_DropAtEcho()`：只丢 AT 回显，保留 `+IPD` 帧 |
| 2 | `ESP8266_SendCmd()` 命中关键字后的 `ESP8266_Clear()` | 同上 | 同上 |
| 3 | `ESP8266_WaitRecive()` 判定"接收完成"时执行 `esp8266_cnt = 0` | 计数清零后，后续字节从缓冲区**下标 0 开始覆盖**，把还没处理的下行帧冲掉（**最隐蔽，最容易被漏掉**） | 只返回"计数已稳定"，**绝不再改动接收缓冲区** |
| 4 | `OneNet_RevPro()` 结尾的 `ESP8266_Clear()` | 处理完一帧就把整个缓冲清掉，缓冲里排队的**下一帧**直接没了 | 删掉；缓冲区管理权统一下放到 `esp8266.c`，协议层不要自己清 |
| 5 | 接收中断里 `if(cnt >= sizeof(buf)) cnt = 0;` | 计数回绕会把一帧数据从**中间截断** | 满时丢掉最旧的 1/4，并维持 `buf[cnt] = 0` 便于 `strstr` |

### 为什么"点开关"特别容易触发

每收到一条下行指令，应用层会紧接着发**两次**（立即上报最新状态 + `set_reply` 回执），
再加上周期上报，**发送窗口累计有几百毫秒**；连点第二下时，指令正好落在这个窗口里被清掉。
所以它是**竞态、偶发**，不是必现——这也是它最难查的原因。

### 正确取帧的两个硬要求

1. **按长度取帧**：不要用 `cnt == cntPre`（两次计数相同）猜"收完了"——
   那会把**半截帧当成完整帧**交给解析层，解析失败后被 `default` 分支静默丢弃。
   必须解析 `+IPD,<len>:` 里的 `<len>`，**凑齐 len 字节才算一帧**。
2. **取帧后拷贝出来**：不要返回接收缓冲区的内部指针，否则后续任何一次清缓冲都会让数据失效。
   应拷到独立缓存（如 `static unsigned char g_IpdFrame[]`），
   缓冲区只负责"把这一帧消费掉"（头部前移），排队中的后续帧继续留着。

### 两个容易被忽略的边界

- **半截帧头保护**：清 AT 回显之前，先看缓冲区**末尾**是不是 `+IPD,` 的一部分
  （帧头只收到一半）。是就**绝对不能清**，否则这一帧永远凑不齐。
- **临界区**：主循环整理缓冲区（丢弃 / 前移）会与串口接收中断**并发**修改 `esp8266_cnt`，
  必须用 `NVIC_DisableIRQ(USARTx_IRQn)` / `NVIC_EnableIRQ()` 包起来；
  中断里只在关中断保护下做移位。移位只有几微秒，远小于一个字节的传输时间，不会丢字节。

### 非阻塞取帧 + 一轮处理完所有帧

- `ESP8266_GetIPD()` 必须支持 `timeOut == 0` 的非阻塞语义。
  ⚠️ 旧实现 `do{...}while(timeOut>0)` 里 `timeOut` 是 `unsigned short`，
  传 0 会递减成 65535 → **变成近似死循环（约 5 分钟）**。
- 主循环应写成"一次把缓冲区里已收到的帧全部处理完"，否则连点时后面的指令会被留到下一轮：

```c
while ((dataPtr = ESP8266_GetIPD(0)) != 0)		/* 0 = 非阻塞，取不到立即返回 */
{
    OneNet_RevPro(dataPtr);
}
```

### 配套：订阅必须用 QoS1，并回 PUBACK

MQTT 规则是 **实际投递 QoS = min(发布方用的 QoS, 订阅时声明的 QoS)**。
订阅时声明 `MQTT_QOS_LEVEL0`，等于告诉服务器"这条主题给我按最多一次发"——
平台即便按 QoS1 推属性设置，到设备也降成 QoS0，**丢了不重发**。

- 订阅用 `MQTT_PacketSubscribe(..., MQTT_QOS_LEVEL1, ...)`
- 收到 **QoS1 的 PUBLISH 必须回 PUBACK**（`MQTT_PacketPublishAck`），
  否则平台认为没送达（重连会重发），订阅 QoS1 也形同虚设。
  注意区分方向：`MQTT_PacketPublish` 的 QoS1 是**上报**方向，订阅的 QoS 管的是**下行**方向，两者互不影响。

### 排查顺序（"设备收不到 App 指令"）

1. 串口有没有 `topic: ...` 那行？
   - **没有** → 丢在"收"这一层，按上面 5 点自查固件
   - **有** → 丢在解析/执行层，看 `params` 内容与回调里的打印
2. 有没有 `Tips: MQTT Publish Send OK`？有 → 只说明**上报方向**传输层通，
   **不代表下行没问题**（上报和订阅是两条独立的路）
3. 有没有 `WARN: 无法识别的MQTT报文`？有 → 收到了半截/错位帧，重点查取帧逻辑
4. **连点 10 次以上**，确认是"必现"还是"偶发"——偶发基本都是缓冲区竞态

> `assets/communication/esp8266.c` 已是修复版；旧实现以 `#if 0` 保留在文件里作对照，
> 生成代码时**直接整份复制**，不要改回旧的清缓冲写法。

## 八、⚠️ 核心坑点 4：发送方向的静默失败（上报"看起来发了"但平台收不到）

### 现象（四个特征同时出现）

- 串口应用层打印正常：`Publish Topic: $sys/.../thing/property/post, Msg: {...}`
- 但**没有** `Tips: MQTT Publish Send OK`（平台没回 PUBACK），物模型数据不更新
- 诡异组合：**订阅能成功**（`Tips: MQTT Subscribe OK` 有），**上报永远失败**
- 用 PC 端 MQTT 客户端（如 MQTTX）用同一套三元组发同样的 JSON → **平台数据正常更新**

> 最后一条是关键判据：**PC 能发成功 = 平台侧没问题**（物模型已发布、标识符/类型/Token 权限都对），
> 问题一定在设备发送方向。

### 根因：`strstr` 遇到二进制帧里的 `0x00` 就"瞎"了

接收缓冲区 `esp8266_buf` 里**同时装着两类东西**：

| 内容 | 是否含 `0x00` |
|---|---|
| AT 应答文本（`OK` / `>` / `SEND OK`） | 无 |
| `+IPD,<len>:` 帧（帧尾是**二进制 MQTT 报文**） | **有** |

SUBACK 帧的实际字节：

```
+IPD,6:  90 04 00 14 00 00
              ↑ 第 3 个字节就是 0x00
```

`ESP8266_SendCmd()` 原来用 `strstr(esp8266_buf, ">")` 找应答关键字——**C 字符串函数遇到第一个 `0x00` 就停**。
所以只要缓冲区开头停着一个还没被应用层取走的 `+IPD` 帧，**帧后面的 `OK` / `>` / `SEND OK` 全部"隐身"**。

### 为什么表现为"订阅能成、上报失败"

```
订阅 SendData：缓冲区干净（只有 SEND OK 文本）→ 拿到 '>' → 93 字节发出去 ✅
              （平台回 SUBACK，帧落进缓冲区）
上报 SendData：DropAtEcho 发现 IPD 帧 → 只丢掉前面的 '+'，**帧留在缓冲区开头**（这是对的，为了不丢下行帧）
              AT+CIPSEND=245 → ESP 回了 OK 和 '>'，但它们被追加在二进制帧后面
              strstr 只能看到 "IPD,6: 90 04" → 找不到 '>' → 死等 2 秒超时
              245 字节一个都没发出去 ❌
```

**两个"正确的设计"撞在一起就出 bug**：`DropAtEcho` 保留帧是对的，但 `SendCmd` 用 `strstr` 查找就踩坑了。

### 为什么一旦发生就"永久失败"（最狠的一层）

`AT+CIPSEND=<len>` 是**两阶段握手**：

```
你: AT+CIPSEND=245      ESP: >            ← ESP 已进入"等 245 字节数据"状态
你: （超时放弃，什么都没发）
ESP: （继续等…）
你(3 秒后): AT+CIPSEND=247\r\n            ← 被当成"数据"吞掉，无回显、无应答
你(6 秒后): AT+CIPSEND=247\r\n            ← 同样被吞
```

之后每一包 AT 指令都被 ESP8266 当作数据吞掉，**自锁**，串口里缓冲区是空的（`buf=[]`）。
**必须给 ESP8266 断电重启才能恢复**（只烧程序不断电救不回来，会卡在 `1. AT` 不往下走）。

### 修复（`assets/communication/esp8266.c` 已修好，复制时三处一起带走）

1. **`ESP8266_FindInBuf()`**：按字节 `memcmp` 查找关键字，不受 `0x00` 影响。
   `ESP8266_SendCmd()` 与 `ESP8266_WaitSendDone()` 都必须用它。
   ⚠️ **绝不要把 `ESP8266_FindInBuf(res)` 改回 `strstr(esp8266_buf, res)`**。
2. **`ESP8266_WaitSendDone()`**：每发完一包等 ESP8266 回 `SEND OK` 再做下一件事，
   避免紧接着的下一包撞上 ESP8266"忙"（回 `busy p...` 而不是 `>`）。⚠️ **不要删掉它**。
3. **拿不到 `>` 时重试一次**（等 300ms 重发 `AT+CIPSEND`），仍失败才打一行 `WARN: CIPSEND %d Failed!`。

### 触发条件与竞态

凑齐这两条才触发：**缓冲区里停着一个二进制 `+IPD` 帧** + **紧接着一条等待 AT 应答的命令**。

- **只上报、不订阅**时不会触发：CONNACK 被 `OneNet_DevLink()` 主动等走，之后的 PUBACK 被主循环及时消费
- **订阅之后立刻上报**最容易触发：`Cloud_Link()` 是同步一气呵成，主循环的取帧还没开始跑，SUBACK 只能滞留
- 换个网络/服务器负载，SUBACK 回得慢一点就可能"不复现"——**属竞态，不是必现**（所以别人机器上"实测可用"）

> 应用层写法建议：**订阅完不要立刻发上报**，让主循环先跑几轮（把 SUBACK 消费掉）再发首报。
> 若确实要"上线立即上报一次"（App 一打开就有数据），本驱动已修复，可以直接用。

### 排查清单（"平台收不到上报"）

1. 串口有没有 `WARN: CIPSEND <len> Failed!`？有 → 就是本节问题（数据一个字节都没发出去）
2. 有没有 `Tips: MQTT Publish Send OK`？
   - **没有** → 传输层没通，按本节查发送方向
   - 有 → 传输层通了，转第六节「物模型未发布 / 标识符 / 类型」排查
3. 用 PC 端 MQTT 客户端用同一套三元组发同样的 JSON：
   - PC 能更新 → 问题在设备发送方向
   - PC 也不能更新 → 问题在平台配置
4. ⚠️ **调试打印缓冲区时不要用 `%s`**：`+IPD` 帧里的 `0x00` 会让打印提前结束，
   你会看到类似 `buf=[IPD,6:?]` 的**假象**，误以为"ESP 没应答"。
   要用带长度的 `%.*s`，或同时打印 `esp8266_cnt`。

### 通用经验（可外推到其他模块驱动）

> **缓冲区里同时装文本和二进制时，查找必须用 `memcmp` + 长度语义，绝不能用 `strstr` / `strchr`。**
> 这是嵌入式串口协议解析里最常见的雷之一；调试打印同样会被 `0x00` 静默截断，把人引向错误结论。
