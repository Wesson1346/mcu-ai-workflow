# 单片机功能联调（S6：系统级验收）

## Overview

前五步做出来的是「一堆各自能跑的模块」。这一步要回答的问题是：

> **把它们放在一起，系统作为一个整体，行为是否和需求清单上写的一致？**

联调不是"再跑一遍看看有没有报错"，而是拿需求清单当验收标准，逐条打勾。

核心两个动作：

- **追溯**：每条需求 → 哪个模块实现 → 哪段代码 → 哪条测试用例
- **回退**：任何问题都能定位到"应该退回第几步修"，而不是在 `while(1)` 里试改

## 第 1 步：输入盘点与追溯矩阵

### 1.1 必须读的四份文档

| 文档 | 取什么 |
| --- | --- |
| `[系统]需求功能清单.md` | 核心功能 / 加分功能（**这是验收标准**） |
| `[系统]功能拆解文档.md` | 模块编号与模块职责 |
| `[系统]硬件搭建文档.md` | 引脚与接线（排查硬件问题时对照） |
| `[系统]模块编程记录.md` | 各模块的验证状态、遗留偏差 |

任何一份缺失 → 说明上游没做完，先回去补，不要凭记忆联调。

### 1.2 建追溯矩阵

逐行填，**每一行都必须有测试用例**：

| 需求编号 | 需求描述 | 实现模块 | 关键代码位置 | 测试用例 | 结果 |
| --- | --- | --- | --- | --- | --- |
| ① | [采集温度] | 模块1 | `bsp_dht11.c: DHT11_ReadData` | 用例1 | ⬜ |
| ② | [超温自动调速] | 模块3 | `main.c: App_Task1000ms` | 用例3 | ⬜ |
| ③ | … | … | … | … | ⬜ |

**发现某条需求没有任何模块实现 → 立刻停下告诉用户**，这是缺功能，不是联调能解决的。

## 第 2 步：单模块冒烟复测

把所有模块放回同一个 `main.c` 后，先确认它们**没有互相干扰**（递加过程中最常见的回归）。

```
□ 每个模块的 Init 都被调用了，且调用顺序与模块编号一致
□ 每个模块单独的功能还能复现（读数 / 显示 / 动作）
□ 没有引脚冲突（对照硬件搭建文档的 7 项冲突检查）
□ 定时器 / 串口 / 中断没有互相抢占
```

任一项不过 → 按 `references/troubleshooting-playbook.md` 的「单独能跑、一起就废」一节处理。

## 第 3 步：主控逻辑联调（重点）

按下面 5 组用例逐条测。**每组都要记录实测值，不接受"应该没问题"**。

### ① 阈值上下沿（最容易出 bug 的一组）

| 用例 | 操作 | 期望 | 关键点 |
| --- | --- | --- | --- |
| 上限触发 | 让温度缓慢升过上限（用电吹风/手捂/电位器模拟） | 风扇全速 + 报警开启 | 临界点是否准确 |
| **回差** | 温度刚回落一点点（仍在阈值附近） | **状态保持**，不立刻关闭 | 没有回差 → 会反复开关 |
| 下限释放 | 温度降到下限以下 | 风扇停 + 报警解除 | 下限值是否合理 |
| 抖动 | 让温度在阈值上下反复小幅波动 | 输出稳定，不抖 | 观察 30 秒 |

### ② 模式切换

| 用例 | 期望 |
| --- | --- |
| 自动 ↔ 手动切换 | 切换后控制权正确转移，手动模式下自动逻辑不再覆盖用户设定 |
| 切换时状态保持 | 切回来时阈值/档位不丢失（或按设计恢复默认） |
| 切换过程无突变 | 风扇不会瞬间全速/骤停（除非设计如此） |

### ③ 报警联动

| 用例 | 期望 |
| --- | --- |
| 报警时本地 + 远程一致 | OLED 显示报警、蜂鸣器响、云平台属性也是报警 |
| 报警可解除 | 条件消失后能恢复，不会卡在报警态 |
| 报警优先级 | 多个条件同时满足时，以最严重的为准 |

### ④ 上电默认状态

| 用例 | 期望 |
| --- | --- |
| 冷启动 | 上电后进入什么模式、什么档位、屏幕显示什么——必须写在文档里并有明确预期 |
| 异常恢复 | 断电重启后不会因为上次的异常状态卡死 |
| 传感器未接 | 上电时传感器没数据，系统不应乱报警（应显示"无数据"或保持安全状态） |

### ⑤ 长按 / 组合键（有按键的系统必测）

| 用例 | 期望 |
| --- | --- |
| 单击 / 长按 / 连击 | 分别触发预期动作，不误触发 |
| 长按计时 | 长按判定时间一致（如 1s），不会时长时短 |
| 边界 | 快速连按不会丢键或多触发 |

## 第 4 步：云平台联调（有 WiFi / OneNET 的系统必做）

按 `references/onenet-selfcheck.md` 的 5 项逐条过。摘要：

| # | 自检项 | 判据 |
| --- | --- | --- |
| 1 | 设备在线 | 平台设备列表显示在线，不是"未激活" |
| 2 | 属性格式 | 上报值是 `{"value": ...}` 包装，bool 用 `true/false` |
| 3 | 写入生效 | 平台属性值真的更新了（**传输成功 ≠ 物模型写入成功**） |
| 4 | 下行闭环 | App 下发 → 设备执行 → `set_reply` 回执，App 显示成功 |
| 5 | 断网重连 | 拔掉路由器再恢复，设备能自动重连 + 重新注册 + 重新订阅 |

第 5 项最容易漏，但也最影响演示效果——答辩现场断网一次就废了。

## 第 5 步：输出联调报告

基于 `assets/integration-test-template.md` 生成 `[系统名称]功能联调报告.md`，包含：

1. 追溯矩阵（全部有实测结果）
2. 五组用例的实测记录（含失败项与修复过程）
3. 云平台 5 项自检结果
4. 遗留问题清单（哪些没修、为什么、影响多大）
5. **3 分钟演示脚本**（答辩/汇报可直接照着走）

## 回退路由表（联调出问题时的唯一处理路径）

| 症状 | 退回哪一步 | 说明 |
| --- | --- | --- |
| 接线松、读数乱跳、模块不供电 | **S4 硬件搭建** | 硬件问题不要在代码里绕 |
| 引脚下错、两个模块抢同一引脚 | **S4 硬件搭建** | 必须重新分配并更新文档 |
| 某模块逻辑/时序错，其他模块正常 | **S5 模块编程**，只重生成该模块 | 不要动主逻辑 |
| 主循环节拍错、任务互相阻塞 | **S5 模块编程**（主控逻辑部分） | 改 `main.c` 的节拍分频 |
| 功能定义含糊（不知道什么算对） | **S1 需求分析** | 先明确验收标准再测 |
| 某个模块没法独立验证、职责重叠 | **S3 功能拆解** | 最贵的回退，顺序变会连带动 S5 |
| 选的型号达不到精度/速度要求 | **S2 硬件选型** | 换型号，然后重走 S4/S5 |
| 云平台连不上、Token/物模型错 | **S6 本步内**改 `onenet.h` 配置区 | 不需要回退上游 |

> 铁律：**一次只退一步、只改一处，改完立刻重测那一条用例。** 同时改两处就失去了因果关系。

## 能力边界

- 不执行编译与烧录，实测现象由用户回报
- 看不到实物，硬件问题靠现象 + 排查表反推
- 无法替代真机长时间稳定性测试；建议用户单独跑一次 30 分钟以上的连续运行

## 注意事项

- **验收标准来自需求清单，不是来自代码**：代码"能跑"不等于"符合需求"
- **不接受"应该没问题"**：每条用例必须有实测值或明确现象描述
- **回退要记录**：在报告里写明退回了哪一步、改了什么，否则下次还会踩
- **遗留问题要如实写**：答辩时被问到"这个功能做了吗"，有记录才不慌
- 联调通过不等于交付完成：还要清理调试代码、把 `MODULE_TEST` 置 0、确认凭据占位符已替换
