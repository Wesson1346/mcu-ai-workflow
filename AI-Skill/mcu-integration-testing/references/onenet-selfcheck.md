# OneNET 云平台 5 项自检

联调时按顺序过这 5 项。**前一项不过不要跳下一项**——后面的现象会混淆判断。

## 前置：配置区确认

打开 `Module/onenet.h` 与 `Module/esp8266.c`，确认占位符都已替换：

```c
/* onenet.h */
#define ONENET_PROID    "你的产品ID"
#define ONENET_DEVID    "你的设备名称"
#define ONENET_TOKEN    "version=2018-10-31&res=products%2F<PROID>%2Fdevices%2F<DEVID>&et=<过期时间戳>&method=md5&sign=<签名>"

/* esp8266.c */
#define ESP8266_WIFI_SSID   "你的WiFi名"
#define ESP8266_WIFI_PWD    "你的WiFi密码"
```

- Token 里的 `et=` 是**过期时间戳**（秒），过期就连不上
- Token 里的 `res=` 必须与 PROID/DEVID **完全对应**，抄错了签名就无效
- WiFi 必须是 **2.4GHz**，ESP8266 不支持 5GHz

---

## 自检 0：平台侧先验（用 MQTT.fx，不碰单片机）

**为什么先做这步**：设备连不上的时候，分不清是"平台配错"还是"单片机代码错"。
用 MQTT.fx 冒充设备端，能先把平台侧彻底排除掉。

| 参数 | 填什么 |
| --- | --- |
| Broker | 见 `AI-Skill/stm32-driver/references/onenet-setup-guide.md` 第七节（课件两种写法不一致，以控制台「设备详情 → 连接参数」为准） |
| 端口 | `1883`（不改） |
| Client ID | **设备名**（要改） |
| User Name | **产品 id**（要改） |
| Password | **Token**（要改） |

**判据三步**：

1. **看灯**：小绿灯 = 连接成功；小红灯 = 连接失败（查上面三项参数）
2. **测上行**：向 `$sys/{产品id}/{设备名}/thing/property/post` 发布
   `{"id":"1","params":{"temp":{"value":28}}}`
   → 控制台「设备详情 → 设备调试」应显示 `temp` 更新为 28
3. **测下行**：订阅 `$sys/{产品id}/{设备名}/thing/property/set`，
   在「设备调试 → 应用模拟器」里选一个 bool 属性下发 `true` → MQTT.fx 应收到报文

**三项全过 → 平台没问题**。此后任何失败都往单片机侧查，不要再怀疑平台配置。

---

## 自检 1：设备在线

**操作**：烧录后看串口打印，再打开 OneNET 控制台 → 设备列表

**判据**：
- 串口有 `OneNet_DevLink` 相关成功输出
- 控制台该设备状态是 **在线**（不是"未激活"）

**不过怎么办**：

| 串口现象 | 原因 | 处理 |
| --- | --- | --- |
| WiFi 连不上 | SSID/密码错；5GHz 频段 | 改 2.4G；核对密码 |
| `AT` 无响应 | USART2 接线反了；波特率不对；CH_PD 没上拉 | 核对 PA2/PA3；ESP8266 默认 115200；CH_PD 接 10k 上拉 |
| CONNACK 返回非 0 | PROID/TOKEN 不匹配 | 重新生成 Token，确认 res 路径 |
| **昨天能连、今天连不上** | **Token 过期**（`et=` 时间戳到期） | 重新生成 Token 并替换 |
| 反复重连 | 信号弱；供电不足 | 看 RSSI；加大电源电容 |

## 自检 2：上报格式正确

**操作**：看串口打印的 JSON，或抓 MQTT 报文

**判据**（三条都要满足）：

1. 属性值必须**带 value 包装**：`{"temp":{"value":26.3}}`，不是 `{"temp":26.3}`
2. bool 必须写 `true` / `false`，**不能写 `1` / `0`**
3. 多属性一次打包成一个 `params` 对象，不要每条发一次

**为什么较真**：OneNET 对 params 是**整包校验**——任何一个字段格式错，**整个包的属性都不会更新**，
表现是"发了但平台没变化"，极难排查。

---

## 自检 3：写入真的生效（最容易被误判的一项）

**操作**：设备端上报后，去控制台看该设备的**属性值**

**判据**：平台上的数值与设备端一致，并且**更新时间在刷新**

**核心认知**：

> **传输层成功 ≠ 物模型写入成功。**
> 串口显示"发送成功"只说明报文发出去了，不代表平台接受了这个属性值。

**不过怎么办**：

| 平台表现 | 原因 | 处理 |
| --- | --- | --- |
| 属性值一直是旧值/空 | 格式不对（回自检 2）或属性标识符（identifier）与平台物模型不一致 | 对照物模型逐字核对 identifier |
| 只有部分属性更新 | 某一个字段格式错导致整包被拒 | 逐个属性二分排查 |
| 值更新但时间不变 | 实际上没写入 | 同上 |

---

## 自检 4：下行闭环

**操作**：在 App（或控制台）下发一条属性设置，如把阈值改成 35

**判据**（四步都要成立）：

1. 设备收到并解析出指令（串口能打印出收到的值）
2. 设备**执行**了动作（如阈值变量真的变了）
3. 设备回了 `set_reply`
4. App 显示"下发成功"，不是一直转圈

**不过怎么办**：

| 卡在哪 | 原因 | 处理 |
| --- | --- | --- |
| 设备完全没收到 | 没订阅 `property/set`；订阅时机太早（DevLink 之前） | 确认订阅在连接成功后执行 |
| 收到但解析失败 | 用 `strstr` 在含 `0x00` 的缓冲区里查找，静默失败 | 改用 `memcmp` + 长度语义（`FindInBuf`） |
| 执行了但 App 显示失败 | 没回 `set_reply` | 补回执 |
| App 一直显示下发中 | 回执主题或报文格式错 | 核对回执主题名为 `property/set_reply` |

**关键提醒**：接收缓冲区里同时装文本和二进制时，**绝不能用 `strstr` / `strchr`**。

---

## 自检 5：断网重连

**操作**：拔掉路由器电源 → 等 30 秒 → 恢复

**判据**：
- 设备能自动检测到断线
- WiFi 恢复后自动重连
- 重连后**重新 DevLink + 重新订阅**
- 平台恢复看到数据上报
- App 恢复可下发

**为什么必测**：答辩/演示现场断一次网就废了。而且"重连了但没重新订阅"是最隐蔽的失败——
设备在线、能上报，但**收不到任何下行指令**。

**不过怎么办**：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 完全不重连 | 断线没检测机制 | 加心跳（PINGREQ）超时判断，超时就重连 |
| 重连了但不订阅 | 重连流程漏了订阅步骤 | 把「连接 → 注册 → 订阅」封成一个函数，重连时整体调用 |
| 重连后内存越来越少 | MQTT 库 malloc 未释放 | 重连前释放旧缓冲 |
| 一直重连失败 | 路由器刚恢复，DHCP 还没好 | 加退避重试（1s → 2s → 5s） |
