# 单片机模块编程（S5：逐模块实现 + 主控逻辑）

## Overview

把「纸面上的系统」变成「能跑的代码」。核心方法论只有一句：

> **一次只做一个模块。接线 → 生成驱动 → 编译烧录 → 验证现象 → 通过后再做下一个。**

这样做的好处是：任何问题都能立刻定位到具体那个模块，不会出现"不知道错在哪"。

本 skill 不自己发明引脚，也不自己决定模块顺序——这两件事在前两步已经定死了，直接读文档。

## 开发阶段：本地优先（来自课件第 13 章）

功能分两段做，**本地全部跑通、能独立运行之后，才碰联网**。

| 阶段 | 包含 | 通过判据 |
| --- | --- | --- |
| **阶段一：本地** | 模块 1..M（**不含通信模块**）+ 本地主控 `main.c` | 拔掉 WiFi 也能完整跑：采集 → 判断 → 显示 → 执行 → 报警 |
| **阶段二：联网** | 通信模块 + `main.c` 接入上报与下行 | 本地功能不退化 |

> ⚠️ **硬红线**：阶段一没通过，不许开始通信模块。
> 通信是最容易出问题的一环；本地还没稳就上云，出错时分不清是本地逻辑还是网络问题。

这个顺序不是拍脑袋定的，来自课件第 13 章的功能开发顺序：本地功能先做（1–5），联网/App 放最后（6–7）。

## 第 1 步：输入锁定（必做，不可跳过）

**在写任何代码之前**，必须先拿到下面两份文档并解析出两张表。缺一份就停下来，不要猜。

### 1.1 模块顺序表（来自功能拆解文档）

读 `[系统名称]功能拆解文档.md`，定位章节 **`## 二、硬件模块清单`**。

按表中**行的先后顺序**得到模块编号 1..N：

- ⚠️ **顺序以文档行序为准，不按需求编号重排**。需求编号是功能视角，模块编号才是实施顺序
- 每个模块要拿到 4 个字段：模块编号 / 模块名称 / 硬件型号 / 接口类型
- 若文档同时给了模块卡片，把卡片里的「验证方法」也一并取出来（后面第 5 步要用）

### 1.2 引脚表（来自硬件搭建文档）

读 `[系统名称]硬件搭建文档.md`，分两处取：

| 来源章节 | 用途 |
| --- | --- |
| `## 四、引脚分配速查` | **主数据源**，取每个模块的信号引脚与接口 |
| `## 六、接线总表` | 交叉复核：电源要求、共地、备注 |

**冲突处理**：两表不一致时，**以「四、引脚分配速查」为准**，并在模块记录里标注「与接线总表不一致，已按速查表处理」。
如果一个模块在速查表里查不到引脚 → **停止**，输出缺口清单让用户补，**绝不自行假设引脚**。

### 1.3 合成「模块实施顺序表」

把上面两张表合并成一张，**这张表是整个 S5 的唯一真相源**：

| 模块号 | 模块名称 | 型号 / 接口 | 驱动文件 | 信号引脚 | 验证现象 | 前置模块 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | [名称] | [型号] / [I2C/GPIO/PWM/ADC/USART] | `Module/bsp_xxx.c/h` | [引脚] | [可观察现象] | — | ⬜ 待做 |
| 2 | … | … | … | … | … | 1 | ⬜ 待做 |

状态取值只有三种：`⬜ 待做` / `✅ 通过` / `⚠️ 有偏差`（有偏差必须写明偏差是什么）。

**这一步的产出要展示给用户确认一次**，确认后才开始写第一个模块。

## 第 2 步：工程前置检查（只做一次）

1. **确认库类型**：交给 `stm32-driver` 第 0 步自动检测。Cube 扩展生成的工程默认是 **HAL**；
   若为 LL 按 HAL 处理；只有在用户明确说明是旧的标准库工程时才按 StdPeriph 生成
2. **确认输出目录**：驱动统一落 `Module/`。目录不存在则新建
3. **确认 CMake 已挂载 Module/**（见 `references/cmake-integration.md`）：
   ```cmake
   file(GLOB MODULE_SOURCES "Module/*.c")
   target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${MODULE_SOURCES})
   target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE Module)
   ```
   缺这三行就补上；**CubeMX 重新生成工程后要复查是否被覆盖**
4. **确认基础延时与打印可用**：HAL 下没有微秒延时，需要 `Module/bsp_delay.c` 提供
   `DelayUs(unsigned short)` / `DelayMs(unsigned short)`；
   串口打印需要基于 `HAL_UART_Transmit` 自己封一个 `UsartPrintf(USART_DEBUG, ...)`

> 第 4 条如果缺失，先补这两个基础模块再往下走——几乎所有传感器驱动都依赖它们。

## 第 3 步：模块循环体（严格按编号，不跳号）

对顺序表里的每一个模块，执行下面 6 个动作，**做完一个才做下一个**：

### ① 出方案卡
向用户说明：本模块要实现什么功能、用哪些引脚、会生成哪两个文件、验证时该看到什么现象。
用户确认后进入 ②。

### ② 生成驱动
调用 `AI-Skill/stm32-driver/SKILL.md`，**一次性传齐 5 个参数**，不要反问用户：

| 参数 | 值 |
| --- | --- |
| 模块名 | 顺序表里的「模块名称」 |
| 引脚 | 顺序表里的「信号引脚」（**已经确定，不要再问**） |
| 库类型 | HAL（或检测结果） |
| 输出目录 | `Module/` |
| 工程约定 | `stm32-driver` 的 8 条强制约定（DelayUs/DelayMs、UsartPrintf、g_ 前缀、判空用 0、sprintf 先格式化、OLED 固定文字用英文…） |

涉 ESP8266 / OneNET / 云平台时，通信层文件（esp8266、onenet、MqttKit、cJSON）**整份复制**
`stm32-driver/assets/communication/`，不要从零重写。

**📖 读取纪律（控制上下文成本，必须遵守）**

| 文件 | 读几次 | 说明 |
| --- | --- | --- |
| `stm32-driver/SKILL.md` | **整个 S5 只读 1 次** | 约 10,500 token。8 条工程约定、编码规范、文件模板读一次就够，**后续模块直接复用，不要重读** |
| `references/sensor-catalog.md` | 每个模块读**对应那一节** | 不要整份读；DHT11 只读 DHT11 那段 |
| `references/hal-guide.md` | 按需读相关小节 | 查 HAL API 时才读 |
| `references/stdperiph-guide.md` | **不读** | 本仓库是 HAL 工程，这份 19.6KB 白读 |
| `references/onenet-setup-guide.md` + `onenet-guide.md` | 只在做通信模块时读 | 平台配置 + 代码坑各一份 |
| `assets/communication/*.c` | **不读内容，只复制** | 复制后在配置区改参数即可；`MqttKit.c` 有 40KB，通读毫无意义 |

> 为什么较真：7 个模块每个都重读 `stm32-driver/SKILL.md` 会多烧约 6 万 token，
> 而且内容完全一样——纯浪费。读一次记住，后面所有模块都用同一套规则。

### ③ CMake 登记检查
新文件落下后，确认 `Module/*.c` 会被 GLOB 收到；若工程用的是显式文件列表，则把新 `.c` 加进去。

### ④ 静态自检（不编译也能查的 6 项）
```
□ 头文件保护宏是否与文件名对应（__BSP_XXX_H）
□ 引脚宏是否用了本模块在顺序表里的引脚值（不是别的模块的）
□ API 是否与库类型匹配（HAL 工程里不出现 GPIO_Init / RCC_APB2PeriphClockCmd）
□ 延时是否用 DelayUs / DelayMs（不是 Delay_us / HAL_Delay 顶替微秒延时）
□ 串口打印是否用 UsartPrintf(USART_DEBUG, ...)（不是 printf）
□ 判空是否用 0（不是 NULL）
```

### ⑤ 单模块验证
在 `main.c` 里用宏控制只跑当前模块：

```c
#define MODULE_TEST  1     /* 改成 0 表示进入完整主控逻辑 */
```

验证期间 `while(1)` 只调用这一个模块的读取/执行函数并把结果打到串口或 OLED。
**编译与烧录由用户用自己的工具完成**，本 skill 只要求用户回报现象。

### ⑥ 记录状态
把结果写进「模块实施顺序表」和 `[系统名称]模块编程记录.md`：

- ✅ 通过 → 进入下一个模块
- ⚠️ 有偏差 → 记下偏差（如「读数偏高 2℃」），判断是否可接受；不可接受则回到 ② 修驱动
- ❌ 未通过 → **不得进入下一个模块**，按 `references/module-sequence-guide.md` 的排错分流表定位

## 第 4 步：本地主控逻辑（查漏补缺，不是从零写）

> **课件第 13 章对这章的定位**：前面各章已经实现了大部分功能模块、主控逻辑也实现了一部分，
> 本章主要是做**本地功能的查漏补缺、修改不合理的地方**。
>
> 所以不要指望"一次生成完美主控"，而是三轮：拼起来 → 跑起来 → 找出不合理 → 改。

### 4.1 阶段一：本地主控（不含通信）

把 `MODULE_TEST` 置 0，**先只调用本地模块**（传感器 / 显示 / 执行器 / 按键 / 报警），
通信模块暂不接入。

必须遵守（★ = 课件要求，☆ = 工程实践补充，课件未提但建议照做）：

| # | 要求 | 来源 |
| --- | --- | --- |
| 1 | 各模块 `XXX_Init()` 按**模块编号顺序**调用（顺序即依赖顺序） | ★ 拆解文档定序 |
| 2 | 变量定义在 `main()` **之外**，全局变量 `g_` 前缀 | ☆ 工程约定 |
| 3 | `while(1)` 用 **1ms 基础节拍 + 计数分频**，禁止 `HAL_Delay(1000)` 这类长阻塞 | ☆ 工程实践 |
| 4 | 阈值控制要有**回差**（超过上限才开、低于下限才关），否则临界值反复动作 | ☆ 工程实践 |
| 5 | 数字先 `sprintf` 再显示；OLED 固定文字用英文 | ★ 字库仅 12 个汉字 |
| 6 | 串口统一 `UsartPrintf(USART_DEBUG, ...)` | ☆ 工程约定 |

**分频建议**（☆）：采集 1s / 显示 100ms / 按键扫描 20ms。

**阶段一验收（硬判据）**：拔掉 WiFi 或通信模块不接电，系统仍能完整运行——
采集 → 判断 → 显示 → 执行 → 报警。做到这一条，本地闭环才算成立。

### 4.2 查漏补缺（这一章真正的活）

本地主控跑起来后，对照《[系统名称]需求功能清单.md》逐条过，找出"不合理的地方"：

| 常见的"不合理" | 怎么改 |
| --- | --- |
| 某模块单测能跑，串起来后失效 | 查引脚冲突 / 定时器抢占 / 中断优先级 |
| 数值在临界点反复跳 | 加回差 |
| 按键反应迟钝或不灵 | 查是否有长阻塞；消抖是否用了计数器而不是 `HAL_Delay` |
| 显示刷新拖累采集 | 显示降频到 100ms 一次 |
| 上电默认状态不符合预期 | 明确默认模式/档位，并写进文档 |
| 传感器读失败时误报警 | 失败时保留上次值，不要直接把 0 写进状态 |

**改完一条立即复测那一条**，不要一次改多处——否则失去因果关系。

### 4.3 阶段二：接入通信

通信模块**单独验证通过后**（第 3 步循环体走完），再改 `main.c`：

1. 加一个 5–10s 的上报任务（☆ 不要每轮都发，会被平台限流）
2. 加下行处理：非阻塞 `ESP8266_GetIPD(0)` 取帧，**不在中断里做长耗时解析**
3. 上报属性必须 `{"value": ...}` 包装，bool 用 `true` / `false`（★ 云平台整包校验）
4. **本地功能不得退化**——加完通信后重跑 4.1 的验收

模板见 `assets/main-c-template.md`（其中的节拍分频、阈值回差属 ☆ 工程实践补充）。

## 第 5 步：交付前总检

```
□ 顺序表里 N 个模块状态是否全部 ✅（或 ⚠️ 已判定可接受）
□ 阶段一验收过：拔掉 WiFi，本地仍能完整运行（采集→判断→显示→执行→报警）
□ 阶段二接入通信后，本地功能无退化
□ 每个 bsp_xxx.c/.h 是否都在 Module/ 下
□ CMakeLists.txt 的 Module 三行是否还在
□ main.c 的 MODULE_TEST 是否已置 0
□ 是否还有写死的测试引脚或调试专用代码
□ 云平台相关：凭据是否仍为 YOUR_ 占位符（提醒用户填自己的）
```

然后把控制权交给 `mcu-integration-testing`（S6 功能联调）。

## 能力边界（务必如实告知用户）

- 本环境**不执行编译和烧录**。skill 生成代码、做静态自检；编译报错与硬件现象由用户用自己的工具验证后回报
- 无法看到实物接线，接线问题只能通过「现象 + 排查清单」反推
- 无法读示波器/逻辑分析仪数据，时序问题要靠降低速率、分段打印来定位

## 注意事项

- **绝不反问引脚**：顺序表里已有引脚，再问用户就是链路断了（这是本 skill 存在的理由）
- **绝不跳号**：模块没验证通过就做下一个，等于把错误叠加
- **绝不自创顺序**：顺序来自功能拆解文档的行序，不是你觉得哪个简单先做哪个
- **一次只改一个模块**：排错时同时改两个模块的代码，就再也分不清是谁的问题
- **不写死引脚在 skill 里**：所有引脚值都从文档来，换项目只换文档
- **本地没跑通不许碰联网**：阶段一（本地闭环）未通过就做通信模块，等于在流动的沙子上盖楼
- **主控是改出来的，不是一次写出来的**：先拼起来跑通，再对照需求找不合理处逐条改
- 若 `Module/` 下已有同名驱动文件，先询问用户是覆盖还是改名，不要直接盖掉
