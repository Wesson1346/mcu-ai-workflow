# 模块顺序编排原则 + 单模块失败排错分流

## 一、为什么顺序不能随便定

模块编程的前提是「一次只做一个、做了就能验证」。
顺序排错会导致：后面做的模块依赖前面还没验证的东西 → 错误叠加 → 定位不到根因。

**顺序的唯一来源是《[系统名称]功能拆解文档.md》的「二、硬件模块清单」行序。**
本文档解释那个顺序为什么这么排，以及在特殊情况下如何判断。

## 二、标准编排原则（来自课件）

| 顺序 | 模块类型 | 为什么排这儿 |
| --- | --- | --- |
| 先做 | 数据源 / 传感器 | 没有数据，后面所有功能都无从验证 |
| 先做 | 显示（OLED） | **兼作调试窗口**，后面每个模块都靠它看值 |
| 再做 | 执行器（风扇 / 电机 / 继电器） | 有了数据和显示，才能验证"动作对不对" |
| 再做 | 交互输入（按键 / 编码器） | 要改参数了才需要 |
| 再做 | 报警 / 提示（蜂鸣器） | 依赖前面判断出的状态 |
| 再做 | 手动模拟量（电位器 ADC） | 用来替代传感器做可控输入，方便联调 |
| 最后 | 通信（ESP8266 / 蓝牙） | 本地全通了，才有必要上云 |

## 二之二、课件第 13 章的 7 步顺序与本 skill 的对应

课件给出的功能开发顺序是 7 步，与本 skill 的模块编号不是一对一关系：

| 课件步骤 | 内容 | 对应本 skill |
| --- | --- | --- |
| 1 | DHT11 温度采集（最基础，不依赖任何模块） | 模块 1 |
| 2 | OLED 显示（先显示固定文字） | 模块 2 |
| 3 | 风扇 PWM（先固定占空比） | 模块 3 |
| 4 | 电位器、按键输入（硬件独立，先验证） | 模块 4、5 |
| **5** | **电位器 + 主控逻辑（本地串联）** | **阶段一收尾 → SKILL.md 第 4 步 4.1** |
| 6 | WiFi 通信，温度上传 OneNET | 通信模块（阶段二） |
| 7 | 手机 App 控制 | S6 联调 / 不在本 skill |

**两处差异，需要知道：**

1. 课件把「电位器和按键」算作同一步（都属于"硬件独立的输入"），本 skill 按硬件拆成两个模块——
   两者一个是 ADC 采样、一个是 GPIO 扫描，验证方法完全不同，合并了反而不好定位问题。

2. **课件 7 步里没有单列蜂鸣器**，它只在章首给了参数表（有源 / GPIO / 3.3V / PB10），
   看起来报警逻辑是随主控逻辑一起加的。
   **本仓库仍把蜂鸣器当独立模块**（能响、能停，单独验证一次），理由是：
   报警在主控里最容易被忽略，单独验证过，S6 联调时才能确定"喇叭本身是好的，问题在判断逻辑"。

> 第 5 步的关键含义：**本地功能全部串起来、能独立运行，才允许做第 6 步（联网）。**
> 这就是 SKILL.md 里那条「阶段一没通过不许碰通信」的来源。

## 三、特殊情况怎么处理

| 情况 | 处理 |
| --- | --- |
| 没有显示模块 | 用串口打印替代"调试窗口"，此时串口驱动必须第一个做 |
| 传感器依赖执行器才能产生变化（如加热片 + 温度传感器） | 执行器提前到传感器之后、交互之前 |
| 多个同类传感器 | 按「先简单后复杂」：数字量（DHT11）先于模拟量（光敏 ADC） |
| 通信模块是唯一数据来源（如从云端下发给本地） | 通信提前到数据源位置，否则后面无法验证 |
| 用户要求先做某个模块 | **可以调整，但必须改文档**：同步更新功能拆解文档的模块编号，否则记录与代码会错位 |

> 判断口诀：**能不能独立验证？** 如果一个模块离开某个尚未完成的模块就无法验证，那它就排在那之后。

## 四、单模块验证失败的排错分流

按下面顺序逐条查，**一条一条排除，不要同时改两处**。

### 第 1 分流：有没有现象（连基本反应都没有）

| 现象 | 最可能原因 | 动作 |
| --- | --- | --- |
| 串口一行字都没有 | 串口没初始化 / 波特率不匹配 / TX-RX 接反 | 先用最小代码只发一行字验证串口 |
| OLED 全黑 | I2C 引脚错 / 地址错 / 没送初始化序列 | 查 SCL/SDA 是否与速查表一致；扫 I2C 地址 |
| 程序不跑、卡死 | 初始化里死等某个标志（如等 DHT11 响应、等 WiFi 连接） | 给所有 `while` 等待加超时退出 |
| 一上电就复位 | 供电不足（ESP8266 启动瞬间电流大）/ 短路 | 单独给模块供电，或加大电源电流 |

### 第 2 分流：有现象但值不对

| 现象 | 最可能原因 | 动作 |
| --- | --- | --- |
| 读数恒为 0 或恒定值 | 传感器没响应、时序不对、引脚接错 | 用 `DelayUs` 逐段打印时序；核对引脚 |
| 读数偶尔跳变 | 时序余量不足 / 中断干扰 / 线太长 | 降低速率；缩短信号线；关键时序关中断 |
| 读数有规律偏移 | 校准问题（如温度偏高 2℃） | 记录偏差，判断是否可接受，必要时加补偿 |
| PWM 没反应 | 引脚不在定时器通道上 / 定时器没使能 / 比较值没更新 | 核对引脚复用表；确认 `HAL_TIM_PWM_Start` 已调 |

### 第 3 分流：单独能跑，接入主逻辑后失效

| 现象 | 最可能原因 | 动作 |
| --- | --- | --- |
| 接了第二个模块后第一个失效 | 引脚冲突 / 定时器被抢占 / 中断优先级问题 | 回查硬件搭建文档的冲突检查 7 项 |
| 加显示后传感器读数错 | 显示耗时太长挤占了时序 | 把显示降频（100ms 一次），关键时序关中断 |
| 加了 `HAL_Delay` 后按键失灵 | 长阻塞 | 改节拍式主循环（见 `main-c-template.md`） |
| 上云后本地卡顿 | MQTT 解析阻塞主循环 | 用非阻塞 `ESP8266_GetIPD(0)`，解析放低频任务 |

## 五、什么时候该回退到上一步

| 症状 | 该退到哪一步 |
| --- | --- |
| 引脚根本不够 / 两个模块必须共用同一引脚 | **S4 硬件搭建**（重新分配） |
| 选的型号拿不到、或驱动资料太少无法生成 | **S2 硬件选型**（换型号） |
| 模块划分本身不合理（一个模块没法独立验证） | **S3 功能拆解**（最贵的回退，会连带动 S5） |
| 功能定义本身含糊（不知道该做什么才算对） | **S1 需求分析** |

> 回退要在 `[系统名称]模块编程记录.md` 里记下原因，否则下次还会踩同一个坑。
